# auto-recipe 開発方針とロードマップ

この文書は、auto-recipe をどの順番で作り、どの時点で何を検証するかをまとめた作業方針である。

`DESIGN.md` に書かれた内容を固定仕様とはせず、実データを使った検証結果に応じて更新する。最終的な判断基準は、実際に料理をするときに「探しやすい」「分量が分かる」「手順に迷わない」ことである。

## 1. 目指すもの

気に入った料理を登録しておく、自分専用の確定版レシピ集を作る。

主な利用場面は次の通り。

1. 今日作る料理を、過去のレシピ集から探す
2. レシピを開き、作る人数に合わせて分量を見る
3. スマートフォンを見ながら料理する
4. 実際に作って気に入ったレシピだけを登録する

新しいレシピを探す段階では、通常どおりWeb検索を使う。auto-recipe は新しいレシピを探すサービスではなく、気に入ったレシピを「殿堂入り」させるための道具とする。

## 2. 基本方針

### X方式を採用する

登録時にレシピを統一フォーマットへ変換し、確認・修正した結果を確定保存する。

- 閲覧時にLLMを呼ばない
- 表示は速く、安定する
- オフライン閲覧を可能にする
- ユーザーの手修正を残す

元ソースから表示のたびに生成するY方式は採用しない。毎回の生成待ちが発生し、ユーザーが行った修正も失われるためである。

### 元ソースは保険として残す

レシピの普段の表示には、確認済みの統一フォーマットを使う。一方で、再変換できるように元URLや抽出済みテキストなどを保険として保持する。

元ファイルそのものを永続保存するかは別途決める。少なくとも、次の情報は残す価値がある。

- 元URL
- 抽出した生テキスト
- OCR結果
- 元ファイルへの参照（必要な場合）
- 変換バージョン

### 再変換はユーザー操作で行う

スキーマやプロンプトを改善した場合は、元ソースから最新状態の候補を作れるようにする。

ただし、再変換結果で現在のレシピを無条件に上書きしない。

```text
現在の確定版
  + 最新ルールでの再変換
  ↓
差分を確認
  ↓
ユーザーが採用
  ↓
新しい確定版として保存
```

これにより、X方式の「手修正が残る」と、元ソースから再生成できる柔軟性を両立する。

## 3. 2つの入力フロー

既存データの移行と、今後の新規登録は分けて扱う。

### A. 新規登録

今後の本命フロー。

```text
Webでレシピを探す
  ↓
URLまたはファイルを投入
  ↓
内容を取得・抽出
  ↓
LLMで統一フォーマットへ変換
  ↓
確認・修正
  ↓
確定保存
```

MVPでは、まずレシピサイトのURLと静的ファイルを対象にする。YouTubeの正規化は将来対応とし、MVPには含めない。

### B. 既存データの移行

現在保存されている約190件を一度だけ変換するフロー。

入力には、テキスト、テキスト抽出可能なPDF、画像PDF、JPEGなどが混在している。したがって抽出処理は、入力形式によって経路を分ける。

```text
テキスト        → テキスト抽出
テキストPDF     → テキスト層の抽出
画像PDF / JPEG  → OCRまたはVision
```

移行は、新規登録フローと共通の最終レシピ形式へ変換する。ただし、変換器の品質が固まる前に190件を一括処理しない。

## 4. 開発フェーズ

### Phase 0：変換パイプラインの検証

UIを作る前に、現在のサンプル10件で変換品質を確認する。

最低限、次の種類を含める。

- テキスト：暗殺者のパスタ
- テキスト：麻婆茄子
- 画像系PDF：なすの肉巻き
- 別サイト由来のPDF：豚ニラ玉など
- 分量や手順に特徴があるレシピ

検証項目は、JSONの形式だけではなく、料理中に使えるかどうかとする。

- 材料が漏れない
- 分量が誤らない
- 元の人数を認識できる
- 分数、範囲、少々、適量を壊さない
- 手順を適切な単位に分割できる
- 手順内の分量を保持できる
- 注意事項やユーザーメモを保持できる
- 人間が短時間で修正できる

この段階ではOpenAI APIを使う。将来のローカルLLM対応は、変換処理を分離しておけば後から検討できる。

### Phase 1：レシピビューア

Phase 0で作った数件のレシピを使い、閲覧体験を検証する。

- レシピ一覧
- タイトル・材料名検索
- 表記ゆれ検索
- カテゴリ検索
- 主要材料検索
- レシピ詳細表示
- 希望人数の入力
- 分量換算
- 手順表示
- 料理中に見やすい表示

このフェーズの成功条件は、次のループが実際に使えることである。

```text
今日なにを作るか探す
  → レシピを選ぶ
  → 人数を変更する
  → 材料と手順を見ながら料理する
```

### Phase 2：登録・修正

URLまたはファイルを入力し、LLM変換後に確認して保存できるようにする。

確認画面では、少なくとも次を編集可能にする。

- タイトル
- 元の人数
- 材料名
- 分量・単位
- 手順
- タグ
- メモ

LLMの変換精度を100%にすることより、80%程度の結果を人間が簡単に直せることを重視する。

### Phase 2.5：Cloudflare公開基盤

Phase 3の一括移行前に、本人が複数端末から使える公開基盤を整える。

- Cloudflare Workers + TypeScript + Hono
- Cloudflare Static Assetsで現在のビューアを配信
- Cloudflare R2へレシピJSONと保存履歴を保存
- Cloudflare Accessで本人だけに利用を許可
- OpenAI APIキーはWorker Secretへ保存
- ローカルの一括変換・検証には既存Pythonツールを継続利用

現在の構成は [`../ARCHITECTURE.md`](../ARCHITECTURE.md) を参照する。

### Phase 3：既存190件の移行

新規登録とビューアを実際に使い、スキーマと変換ルールが安定してから行う。

推奨する順番は次の通り。

1. サンプル10件で検証
2. 20〜30件で実運用テスト
3. 問題を修正
4. 残りを一括変換
5. 失敗・要確認のレシピだけ手動確認

### Phase 4：再変換・将来拡張

必要になった時点で追加する。

- スキーマ・プロンプト更新後の再変換
- YouTube URLの字幕・概要欄からの正規化
- OCRや構造化処理のローカル化
- 高度な検索
- Dropboxとの連携
- ネイティブiPhoneアプリ

これらはMVP成立の前提ではない。

## 5. レシピデータの考え方

最終的なデータ形式は、料理中の表示と編集のしやすさを優先して決める。現時点では次の要素を想定する。

```json
{
  "id": "nasu-nikumaki-sukiyaki",
  "title": "なすの肉巻き 甘辛すき焼き風",
  "title_reading": "なすのにくまき あまからすきやきふう",
  "source": {
    "type": "url",
    "url": "https://...",
    "site": "..."
  },
  "servings": 2,
  "ingredients": [],
  "steps": [],
  "tags": [],
  "time_minutes": 20,
  "notes": [],
  "raw_text": "...",
  "conversion_version": "..."
}
```

### 人数と分量

元レシピの人数を保存し、表示時に希望人数へ換算する。1人分へ事前に正規化しない。

材料ごとに、人数に応じて換算するかどうかを持たせる。

- 線形換算するもの：肉、野菜、液体など
- 換算しない、または注意が必要なもの：塩少々、適量、揚げ油、卵など

分量は数値だけでなく、分数・範囲・自由記述を扱えるようにする。

### 手順

手順も統一フォーマットの中心に含める。

- 1ステップ1動作を基本とする
- 長い一文を適切な単位に分割する
- 材料と手順を料理中に追いやすい順序で表示する
- 元の注意書きやコツを失わない

手順内の分量は、料理中の利便性のため保持する方向とする。最初から完全な連動を必須にせず、次の段階で進める。

1. 手順内の分量を元テキストとして保持
2. 材料欄を人数換算の正確な情報とする
3. 手順中の分量を材料IDに紐づける
4. 表示時に手順内の分量も換算する

### カテゴリと主要材料

これはMVPに含める。auto-recipeの中心的な探し方が「手元にある材料から今日作るものを決める」ためである。

料理ごとに次を保存する。

- `categories`：主食、主菜、副菜、汁物、丼・ごはん、麺、パン・軽食、おつまみなど
- `main_ingredients`：豚肉、鶏肉、魚、卵、豆腐、なすなど、料理の中心となる材料

全材料検索も残すが、主要材料への一致を高く評価する。たとえば「豚肉」で検索した場合、豚バラ肉・豚こま切れ肉・豚ひき肉を主要材料とする料理を上位に表示し、調味料や少量の具材として豚肉が含まれる料理は下位にする。

MVPでは、複雑なタグ編集画面や意味検索は作らない。検索ボックスとカテゴリ絞り込みを用意し、LLMが登録時に付与した主要材料を使う。

## 6. 技術方針

Phase 0〜2はWebアプリ、必要に応じてPWAとして実装する。

```text
フロントエンド：Webアプリ / PWA
変換処理      ：OpenAI API
保存          ：小さなバックエンド＋DBを基本候補とする
閲覧時        ：LLMを使わず、保存済みJSONを表示
```

変換処理はアプリ本体から分離する。

```text
Extractor       入力からテキストや画像情報を取り出す
Normalizer      抽出結果を統一レシピへ変換する
RecipeStore     レシピを保存・更新する
RecipeViewer    検索・換算・表示する
```

この分離により、OpenAI APIからローカルLLMへの差し替えや、将来のiPhoneアプリ化を妨げない。

## 7. 現時点で決めないこと

次の項目は、実データとビューアを試してから決める。

- 最終的なタグ体系
- 高度な意味検索や埋め込み検索
- 元PDF・JPEGの永続保存方針
- Dropboxとの同期方法
- ローカルLLMの採用
- YouTube対応
- ネイティブiPhoneアプリ

次に実施する作業は以下とする。

2. サンプル10件を入力にできる抽出処理の作成

4. 変換結果の人手レビュー
5. 人数換算ルールの検証

> 変換されたレシピを、実際の料理で安心して使えるか。

この問いに答えが出てから、登録画面、保存場所、190件の移行を進める。
