# auto-recipe 設計メモ

自分専用のレシピ集アプリ。気に入った料理を「殿堂入り」させ、
フォーマットと分量を統一して、いつでも取り出せるようにする。

## 課題（現状：Dropboxに静的ファイル190件）
- フォーマットが不統一（きれいなtxt / テキスト抽出できるPDF / 画像に焼き込まれたPDF・JPEG）
- 分量が1人分・2人分などバラバラ
- ファイル名でしか検索できない
- なす／ナス／茄子 が混在で一発ヒットしない

## ユースケース（重要）
1. **今日なに作る → 過去のレシピ集から探す。** 探した結果＝これから作るもの。（毎日の本命ループ）
2. **新しいレシピをWebで探す時は、このアプリを通さない。** 頭で計算して作る。
3. **実際に作って気に入った → はじめてレシピ集に登録する。** ← アプリを使うのはこの瞬間だけ。登録は“たまの殿堂入り”行為。

## アーキテクチャ決定：X方式 ＋ 元ソース保険 ＋ オンデマンド再変換
- **X方式**：登録時に統一スキーマへ変換して**確定保存**。以後いつ開いても同じものが一瞬で出る（オフラインOK）。
- **手で直せて、直しは残る**（例：「水420は多い→350」を恒久保存）。← 実務で効く決定打。
- **元ソースは保険で併存**：正本は元ソース、統一スキーマは派生（いつでも作り直せる使い捨て）。
- **「最新状態に更新」**：スキーマ/プロンプトを改良したら、元ソースから**再変換**して作り直せる（自動ではなくユーザー操作で。Yの良さをオンデマンドで内包）。

### なぜYではないか
Y方式（元ソースだけ保存し、表示のたびに端末で生成）は「モデルと共に育つ」魅力があるが、
**手で直した分が開くたびに消える**・**開くのに生成待ち**・**検索メタは結局先に作る必要がある**ため、
毎日キッチンで使う殿堂入りコレクションには合わない。

## データフロー
```
[登録（たまに）]
  URL/ファイル投入 → 抽出（テキスト層 or OCR/Vision） → OpenAI APIで統一スキーマ化
    → 確定保存（統一JSON ＋ 元ソース）

[閲覧（毎日・LLM不要・オフラインOK）]
  検索（reading/aliasesでなす/ナス/茄子を吸収） → レシピ選択
    → 人数入力 → 分量換算（ただの算数）して表示
```

## 統一スキーマ（たたき台）
```json
{
  "id": "nasu-nikumaki-sukiyaki",
  "title": "なすの肉巻き 甘辛すき焼き風",
  "title_reading": "なすのにくまき あまからすきやきふう",
  "source": { "type": "url", "url": "https://...", "site": "delish kitchen" },
  "servings": 2,
  "ingredients": [
    { "name": "茄子", "reading": "なす", "aliases": ["ナス","なす"],
      "amount": 2, "unit": "本", "scalable": true },
    { "name": "塩", "amount": null, "unit": "少々", "scalable": false }
  ],
  "steps": ["なすを乱切りにする", "..."],
  "tags": ["ナス","肉巻き","和風","主菜"],
  "time_minutes": 20,
  "notes": "水420は多いかも",
  "raw_text": "...抽出した元テキスト（軽量な保険）..."
}
```
設計判断：
- `servings` は元の人数を保存（1人分正規化しない）。表示時に希望人数へ換算。
- 材料ごとに `scalable`：「塩少々」は人数で増やさない。
- `reading` + `aliases` で検索の表記ゆれを吸収（那須は誤ヒットしない）。
- `raw_text` は軽量な保険（再変換・ミス追跡用）。

## 技術選定
- **フロント**：Webアプリ（PWA）。作者はWeb熟練SWE、得意分野。
  - X方式で表示時にオンデバイスLLMが要らないため、ネイティブSwiftは必須でない。
  - 注意：iOSのPWAは「共有→登録」が弱い → iOSショートカット or URL貼り付けで代替（登録はたまの行為なので許容）。
- **変換LLM**：まずOpenAI API。登録は稀なのでコスト・依存とも軽微。
- **保存場所**：未決（後述）。

## Phase 計画
| Phase | 中身 | LLM | 備考 |
|---|---|---|---|
| 0. パイプライン検証 | 実データ数件をOpenAI APIで統一スキーマ化し「使えるか」検証 | OpenAI API | UI非依存・最重要 |
| 1. ビューア | 検索・表示・人数換算（読むだけ） | 不要 | 毎日の本命 |
| 2. 登録 | URL投入→OpenAI API→確定保存＋再変換ボタン | OpenAI API | |
| 3.（任意）オンデバイス化 | 変換を端末LLMへ | ローカル | want であって need ではない |

## 決定事項
- 保存の主役は統一フォーマット、正本は元ソース（X＋元ソース保険）。
- フロー分離：新規登録（URL） / 既存190件の移行（1回きり）。
- servings は元の人数保存＋scalableフラグ＋表示時換算。
- 検索は reading/aliases で表記ゆれ吸収。
- 手順も統一スキーマに含める（1ステップ1動作に整形）。
- LLMはOpenAI APIでまず作る。
- YouTube正規化は後回し（MVP外）。
- フロントはWebアプリ（PWA）。

## 未決事項（次に詰める）
1. **検索軸／tags設計**：普段どう探すか（材料が余ってる／気分／時間／ジャンル）。
2. **手順の中の分量**：A（書かない・推奨）/ B（元のまま固定）/ C（材料と連動）。
3. **保存場所**：小さなバックエンド＋DB / 既存Dropbox API / ローカルファースト（IndexedDB）＋エクスポート。
4. **移行(B)のタイミング**：Phase 1で新規数件を固めてから190件一括、で良いか。
